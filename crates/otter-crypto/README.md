# otter-crypto

OtterOS's own cryptography, written from scratch: SHA-256/384/512, HMAC, HKDF,
ChaCha20-Poly1305, AES-128/256-GCM (constant-time software, AES-NI/PCLMULQDQ
hardware) and X25519. `#![no_std]` + `alloc`, `#![deny(unsafe_code)]` except
the CPUID-gated `hw` module (`#![allow(unsafe_code)]`, every block with a
`// SAFETY:` comment), zero external dependencies (DECISIONS.md D2, D22, D27)
-- the hash, MAC, key-derivation, AEAD and key-exchange primitives TLS 1.3
will need (a later brief), proven against FIPS/RFC/NIST test vectors and
Project Wycheproof before any network code uses them.

## Layout

| Module | What it does |
| --- | --- |
| `ct` | Best-effort constant-time helpers: `Choice`, `ct_eq`, `select_u8`, `Zeroizing<T>` |
| `hash` | The `Hash` trait (so HMAC/HKDF/TLS can pick SHA-256 or SHA-384 by cipher suite) and `Digest` |
| `sha256` | SHA-256 (FIPS 180-4) |
| `sha512` | SHA-512 and SHA-384 (share one 64-bit compression function, different IV/truncation) |
| `hmac` | HMAC (RFC 2104), generic over `Hash` |
| `hkdf` | HKDF-Extract/-Expand (RFC 5869), generic over `Hash` |
| `chacha20` | The ChaCha20 block function and keystream (RFC 8439 sections 2.3/2.4) |
| `poly1305` | Poly1305 (RFC 8439 section 2.5), 26-bit-limb accumulator |
| `aead` | AEAD_CHACHA20_POLY1305 (RFC 8439 section 2.8) and the `Aead` trait both AEADs implement |
| `aes` | Constant-time software AES-128/256 (FIPS 197), encryption only: a table-free S-box (GF(2^8) inversion via `x^254`, not a lookup) |
| `ghash` | GHASH (NIST SP 800-38D), constant-time GF(2^128) multiplication |
| `gcm` | AES-128/256-GCM: `Aes128Gcm`/`Aes256Gcm`, 96-bit nonces, `seal_in_place`/`open_in_place`, software or AES-NI/PCLMULQDQ |
| `hw` | CPUID-gated AES-NI/PCLMULQDQ (this crate's only `unsafe`); compiles to nothing off x86_64 or without SSE2 |
| `x25519` | X25519 (RFC 7748): 5x51-bit-limb field arithmetic, Montgomery ladder |

Secret-dependent code avoids secret-indexed table lookups and secret-dependent
branches (`ct::ct_eq`, `poly1305`'s final reduction, `aes`'s S-box, `ghash`'s
multiply, `x25519`'s field ops); see `ct`'s module doc for the honest caveats
of doing this in safe Rust. AES uses the constant-time software path unless
AES-NI is present (DECISIONS.md D22); either way GCM's own construction
(padding, counters, tag comparison) is identical.

## Testing

```sh
cd crates
cargo test -p otter-crypto                                          # unit + integration tests (host, aarch64)
cargo test -p otter-crypto --target x86_64-apple-darwin             # same, plus AES-NI/PCLMULQDQ (Rosetta 2)
cargo clippy -p otter-crypto --tests -- -D warnings                  # lint
cargo build -p otter-crypto --target x86_64-unknown-none             # proves it's genuinely no_std
cargo run -p otter-crypto --release --example throughput             # MB/s, for the record
```

`hw`'s AES-NI/PCLMULQDQ intrinsics need `target_feature = "sse2"` in addition
to `target_arch = "x86_64"`: the kernel's own `x86_64-unknown-none` target is
soft-float with SSE disabled at the ABI level (DECISIONS.md D13), so `hw`
compiles to nothing there too (CPUID detection still works; there is simply
nothing for it to hand back). Only `x86_64-apple-darwin` under Rosetta 2
actually exercises the hardware path.

Every primitive's unit tests hardcode its own FIPS/RFC/NIST vectors (180-4,
197, 2104, 4231, 5869, 7748, 8439, SP 800-38D) directly, including RFC 8439
Appendix A.3's eleven Poly1305 edge cases and RFC 7748's 1/1000-iteration
Montgomery-ladder self-composition (1,000,000 behind `--ignored`, too slow for
routine runs). Integration test files need vectors fetched and generated by
tooling (not committed as raw JSON, so the tests need no JSON parser):

```sh
../scripts/gen-crypto-vectors.py   # -> tests/vectors/*.txt
```

That script downloads Project Wycheproof's HMAC-SHA-256/384/512,
HKDF-SHA-256/384/512, ChaCha20-Poly1305, AES-GCM and X25519 vectors
(SHA-256-pinned) and converts them to compact pipe-delimited fixtures, and
separately cross-checks this crate's SHA-256/384/512 against Python's
`hashlib` for a seeded-random message at every length 0-1100 bytes (catches
padding-boundary bugs). `tests/hw_sw_differential.rs` independently fuzzes
10,000 random `(key, nonce, aad, plaintext)` cases per AES-GCM key size,
asserting the hardware and software paths agree (skipped, not failed, on a
host without AES-NI/PCLMULQDQ).
