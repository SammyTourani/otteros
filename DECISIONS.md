# Architecture decisions (append-only; reference by ID)

- **D1 Target.** x86_64, UEFI-first, legacy BIOS also working (Limine hybrid ISO). The final demo boots from a USB stick on an arbitrary cheap laptop.
- **D2 Language and crates.** Rust nightly, target `x86_64-unknown-none`. Allowed external crates: `limine` (boot protocol structs only), `bitflags`, `spin` (may later be replaced by our own locks). Forbidden: `x86_64`, `bootloader`, `uefi`, `smoltcp`, `fatfs`, `embedded-graphics`, `acpi`, `linked_list_allocator`, `buddy_system_allocator`, `pc-keyboard`, `virtio-drivers`, or any crate implementing OS logic. Ours: GDT/IDT, paging, allocators, scheduler, drivers, VFS, FS, TCP/IP, window system. Reason: the public claim is that the AI wrote the OS.
- **D3 Bootloader.** Limine (binary release branch), base revision 3. Requests: framebuffer, HHDM, memory map, RSDP, modules, executable address/cmdline; SMP later. Gives a linear framebuffer + memory map on UEFI, BIOS and real hardware.
- **D4 Kernel shape.** Monolithic kernel in the higher half (0xffffffff80000000); userspace processes with their own page tables. Simplest path to a usable system in weeks.
- **D5 Feedback channels.** Serial COM1 for logs/test results; `isa-debug-exit` (port 0xf4) for pass/fail; QMP `screendump` PNG for visual checks. Cheap, machine-readable, no GUI required.
- **D6 Boot modes.** One kernel binary; behaviour selected by the Limine command line (`test`, `test panic`, later `gui`, `headless`). Two generated limine.conf variants.
- **D7 Storage.** virtio-blk in QEMU first; NVMe then AHCI for real hardware. FAT32 on disk (USB sticks are FAT; macOS can read the results). Own VFS above it.
- **D8 Networking.** virtio-net (QEMU) and Intel e1000/e1000e (QEMU + many real laptops). Own stack: Ethernet, ARP, IPv4, ICMP, UDP, DHCP, DNS, TCP. HTTP only, no TLS. QEMU user-mode networking provides DHCP/DNS/NAT for tests.
- **D9 Input.** PS/2 keyboard + mouse via i8042 (QEMU and most laptops' built-in keyboard/touchpad). USB HID is a stretch goal.
- **D10 GUI.** Userspace display server owns the framebuffer; clients draw into shared-memory buffers; message-passing IPC. Kernel provides framebuffer mapping, IPC, shared memory. App crashes do not take the OS down.
- **D11 Assets.** Permissively licensed bitmap fonts embedded as data (public-domain 8x8 / 8x16). Assets are not "code" for the purpose of the claim; record their licence in THIRD_PARTY_NOTICES.md.
- **D12 Out of scope.** Wi-Fi, TLS, sound, 32-bit, SMP scheduling (may come later), full USB stack (stretch).
- **D13 FPU/SIMD state.** The kernel is compiled with soft-float and no SSE/AVX, so kernel code never touches XMM/YMM registers and trap stubs save only the 15 GPRs. User FPU/SIMD state is saved and restored per process at context switch (FXSAVE/XSAVE into the process control block, M2), not on every trap. Kernel code that needs SIMD later must do explicit save/restore around it.
- **D14 Fault-path logging.** Exception handlers, the double-fault/NMI paths and the panic handler log through a lock-free emergency serial writer, never through the normal locked console, so a fault taken while a lock is held cannot deadlock. Each IST stack has a re-entry guard that halts with a message instead of corrupting itself.
- **D15 Virtual address layout (4-level paging, KASLR off in limine.conf).** HHDM at the offset Limine reports (kept identical in our own tables so early pointers stay valid). Kernel image at 0xffff_ffff_8000_0000 (top 2 GiB, kernel code model), mapped W^X with NX. Kernel dynamic region 0xffff_c000_0000_0000..0xffff_cfff_ffff_ffff for kernel stacks (each with an unmapped guard page below), MMIO windows and a future vmalloc. User space 0x0000_0000_0040_0000..0x0000_7fff_ffff_ffff (M2). PML4 entries 256..511 are shared by every address space.
- **D16 Syscall ABI.** `syscall`/`sysret`. Number in rax; arguments rdi, rsi, rdx, r10, r8, r9; result in rax, negative values -1..-4095 are `-errno` (Linux convention, so userspace helpers are simple). rcx and r11 are clobbered by the instruction. Kernel switches to the per-thread kernel stack from the TSS RSP0 / a per-CPU scratch area; user FPU state is saved lazily per thread (D13).
- **D17 Process model.** A process owns an address space, a file-descriptor table (M3), an exit code and a parent; threads belong to a process (one thread per process at first, threads API later). No `fork`: `spawn(path, argv)` creates a fresh process from an ELF in the VFS/initramfs. `wait(pid)`, `exit(code)`, `yield`, `sleep_ms`, `getpid`. A fault in ring 3 kills only that process and logs it.
- **D18 Userspace binaries and layout.** Static, non-PIE ELF64 linked at 0x0000_0000_0040_0000; 16 MiB stack ending at 0x0000_7fff_ffff_f000 with a guard page; anonymous memory via `map_anon(len)`/`unmap`; argv/envp copied onto the initial stack SysV-style. Userspace crates target `x86_64-unknown-none` with their own linker script and a tiny runtime crate (`libotter`). The initramfs is a ustar archive passed as a Limine module; `init` is `/bin/init`.
- **D19 Time.** LAPIC timer at 1 kHz is the scheduler tick and monotonic clock (`uptime_ms`); TSC is used for fine calibration only; wall-clock from the CMOS RTC arrives with the file system (timestamps).
- **D20 Vision v2 (2026-09-23; supersedes the scope limits in D9 and D12).** OtterOS is an AI-written OS with an AI inside it. The final demo is three moments on a real laptop: (1) cold boot to a designed desktop, (2) Otter, a local language model on OtterOS's own inference engine, chatting offline, (3) agent mode: Claude, reached through OtterOS's own TCP/IP and TLS 1.3, operating the OS through human-approved tool calls. Now in scope: SMP, SIMD, TLS 1.3 and its cryptography, xHCI with USB HID and mass storage. Still out: Wi-Fi, sound, 32-bit.
- **D21 Inference runtime.** Userspace crate; Llama-family architectures only; Q8 group quantization (32 weights per f32 scale) for matmuls, f32 activations; scalar, SSE2 and AVX2 kernels chosen by CPUID at runtime; parallel over user threads. Models use our own `.otm` format made by a host converter. Weights come only from Apache-2.0 or MIT licensed models; they are data (like fonts, D11), recorded in THIRD_PARTY_NOTICES.md and never committed. Correctness is proven by golden logits from a host reference, not by reading generated text.
- **D22 Cryptography.** Written from scratch in a no_std crate with no dependencies. Secret-dependent code is constant-time (no secret-indexed tables, no secret branches); AES uses a constant-time software path unless AES-NI is present. Every primitive ships with RFC vectors and, where they exist, Project Wycheproof vectors (test data fetched at build time). TLS 1.3 only; any verification failure aborts the handshake. The root store is a small embedded subset of the Mozilla CA list (data; MPL-2.0 noted).
- **D23 Agent safety.** Tools that change state (write_file, run_command, open_app, any fetch that sends a body) need an on-screen Allow/Deny from the human; read-only tools may auto-run; an action log shows every call. API keys live only in `/config/anthropic.key` on the data partition, created by the human, never in git, logs, screenshots or panic output. Automated tests never call real LLM APIs; they use a mock server with a test CA.
- **D24 Visual quality.** The desktop must look designed, not retro: TrueType outlines rasterized with anti-aliasing (own parser and rasterizer, an embedded OFL font), alpha compositing, rounded corners, soft shadows, one coherent theme. The orchestrator judges screenshots at every GUI gate.
- **D25 Multicore.** Application processors start via the Limine MP request (a bootloader facility, like the memory map) and are then fully managed by the kernel: per-CPU GS area, per-CPU run queues, IPIs for reschedule and TLB shootdown. xAPIC and x2APIC both supported. AVX state via XSAVE/XRSTOR sized from CPUID leaf 0xD.
- **D26 Loop resilience.** Usage-limit interruptions are expected. A cut-off agent is resumed with SendMessage (context and partial work intact), never replaced. A session heartbeat (CronCreate; fires only when idle) restarts the loop after a stall and is re-created when it expires after 7 days.
- **D27 Pure crates, host-tested.** Libraries with no OS dependencies (graphics, fonts, PNG/inflate, crypto, TLS state machine, JSON, HTML, LLM math) live in `crates/<name>` as `#![no_std]` + `alloc` crates with zero external dependencies. They are unit-tested on the Mac with `cargo test` (fast, no QEMU) and linked into userspace programs by path. `crates/` has its own cargo workspace and config so the kernel's root `.cargo/config.toml` never applies. Independent pure-crate tasks may run in parallel with kernel tasks because they touch disjoint directories.
- **D28 SSD-first storage (Sammy's machine rule, 2026-09-24).** When `/Volumes/SammyDisk` is mounted, `scripts/env.sh` sets `OTTEROS_BUILD_ROOT` and `scripts/ssd-links.sh` keeps `build/`, `kernel/target`, `user/target`, `crates/target` and `third_party/` (downloaded dependencies) as symlinks onto the SSD, recreating them if a clean step removes them. Downloads also go to the SSD: model weights under `OTTEROS_MODEL_DIR` (`/Volumes/SammyDisk/models/otteros`). Other machines are unaffected; `OTTEROS_NO_SSD=1` opts out.

## D29 — Kernel CSPRNG: HMAC_DRBG over a health-tested entropy pool (2026-09-24)
The kernel random generator is NIST SP 800-90A HMAC_DRBG (SHA-256) seeded from an entropy pool of
RDSEED/RDRAND and TSC-jitter samples guarded by SP 800-90B continuous health tests, instead of the
ChaCha20 DRBG named in the first PLAN draft. HMAC_DRBG has official CAVP known-answer vectors, so its
correctness is provable on the host; its throughput far exceeds getrandom's needs (a TLS handshake
uses about 100 random bytes).
