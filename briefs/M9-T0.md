# Brief M9-T0 — `otter-claude`: a Messages API client with streaming and tool use (pure crate)

## Goal
The library OtterOS's agent mode uses to talk to Claude: build Messages API requests, parse the
streaming response event by event, run the tool-use loop correctly, and handle refusals, errors and
limits. Tested entirely offline against recorded streams and a local mock server; no test calls the
real API (D23).

## Applies
D2, D23 (keys never logged; tests never call real LLM APIs), D27 (pure no_std + alloc, zero external
dependencies; path dependencies on otter-json and otter-http).

## Scope and boundaries (another agent works in kernel/ and user/ concurrently)
New crate `crates/otter-claude/`, `scripts/claude-mock-server.py`, fixtures under
`crates/otter-claude/tests/fixtures/`. Do not touch kernel/, user/, GNUmakefile or other crates.
Do not run gmake or QEMU. Do not contact api.anthropic.com.

## Wire protocol (raw HTTP; there is no official Rust SDK)
- `POST https://api.anthropic.com/v1/messages` with headers `content-type: application/json`,
  `x-api-key: <key>`, `anthropic-version: 2023-06-01`, and `anthropic-beta:
  server-side-fallback-2026-07-01`.
- Default body: `{"model": "claude-opus-5", "max_tokens": 64000, "stream": true,
  "fallbacks": "default", "thinking": {"type": "adaptive", "display": "summarized"},
  "output_config": {"effort": "high"}, "system": ..., "tools": [...], "messages": [...]}`. The model,
  effort and max_tokens are configurable; `fallbacks` is on by default (a declined request is
  re-run server-side on another model; the response's `model` field says which served it).
- Tools: `{"name", "description", "input_schema", "eager_input_streaming": true}`; `tool_choice`
  stays `auto` (forced tool choice is rejected by some current models). With eager streaming the
  API does not validate tool input, so the client validates the parsed input against the tool's
  JSON schema (types, required properties, enums, no extra properties when
  `additionalProperties: false`) before execution; an invalid or unparseable input becomes a
  `tool_result` with `is_error: true` and content `INVALID_JSON: <reason>` instead of running.
- Stream events (server-sent events): `message_start` (message object: id, model, usage),
  `content_block_start` (index + block: `text`, `thinking`, `tool_use` {id, name, input}, and
  `fallback` blocks recording a model switch), `content_block_delta` (`text_delta`,
  `thinking_delta`, `signature_delta`, `input_json_delta` {partial_json}), `content_block_stop`,
  `message_delta` (stop_reason, usage), `message_stop`, `ping` (ignore), `error` ({error: {type,
  message}}). Unknown event or block types are preserved and ignored, never fatal.
- Stop reasons: `end_turn`, `tool_use`, `max_tokens`, `refusal` (check it before using content;
  a refusal after fallbacks means the whole chain declined), `pause_turn` (continue by re-sending).
- Tool loop: append the assistant message with every content block exactly as received (thinking
  blocks with their signatures, text, tool_use, fallback blocks), then one user message holding a
  `tool_result` for every `tool_use` of that turn (`tool_use_id`, `content`, `is_error` when it
  failed), in a single message even for parallel calls. Never edit earlier turns.

## API
`Client::new(config)` (API key held as an opaque secret type whose Debug/Display print
`<redacted>`); `Conversation` (system, tools, messages); `Conversation::stream_turn(transport,
&mut on_event) -> TurnResult` where events are `Text(delta)`, `Thinking(summary delta)`,
`ToolUseStart{id, name}`, `ToolUseReady{id, name, input}`, `Stop(reason)`, `Error`; a helper that
runs the loop with a caller-supplied tool executor and an approval hook (D23), stopping after a
configurable number of turns. Usage accounting accumulated per turn.

## Tests (host)
- Fixture SSE transcripts written from the documented format: plain text; thinking then text;
  a single tool_use whose `input_json_delta` fragments split mid-token; two parallel tool_use
  blocks; a refusal; a mid-stream `error` event; `max_tokens`; a fallback block; unknown event and
  block types. Each is parsed from one-byte and random splits with identical results.
- Request building: exact JSON for a two-turn tool conversation (golden file), thinking blocks and
  signatures echoed unchanged, all tool results in one user message.
- Tool-input validation: valid inputs pass; missing required, wrong type, extra property and
  truncated JSON produce the `INVALID_JSON` error result.
- Mock server (`scripts/claude-mock-server.py`, stdlib only, 127.0.0.1): checks the headers
  (`anthropic-version`, beta header, presence of `x-api-key`) and body shape, replays a scripted
  multi-turn tool conversation over SSE; the loop helper completes it end to end via otter-http
  over std TCP with an auto-approving hook, and a denying hook yields `is_error` tool results.
- The key never appears in any log line, error message or Debug output (test by formatting).
