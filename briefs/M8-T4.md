# Brief M8-T4 — `otter-x509`: strict DER, X.509 certificates, path validation, hostname checks, root store

## Goal
Decide, exactly like a careful TLS client, whether a server's certificate chain is trustworthy for a
host name at a given time: strict DER parsing, path building to an embedded trust anchor, every
signature verified with otter-crypto, RFC 5280 constraints enforced, RFC 6125 name matching.

## Applies
D2, D22 (any verification failure rejects), D27.

## Scope and boundaries (another agent works in kernel/ and user/ concurrently)
New crate `crates/otter-x509/` (depends only on `otter-crypto` by path; add it to the crates/
workspace), `scripts/fetch-roots.py`, `scripts/make-test-pki.sh`, `scripts/capture-chains.py`,
fixtures under `crates/otter-x509/tests/`, an appended THIRD_PARTY_NOTICES.md section. Do not touch
kernel/, user/, GNUmakefile or other crates' sources. Do not run gmake or QEMU.

## Design
1. DER reader: definite, minimal lengths only; tag classes and constructed bit; bounded nesting
   depth; INTEGER minimal encoding; BIT STRING unused-bit rules; OID decoding; UTCTime and
   GeneralizedTime per RFC 5280 §4.1.2.5 (Z required, seconds required); any trailing bytes are an
   error. Errors are values; malformed input never panics.
2. Certificates (RFC 5280): keep the raw tbsCertificate bytes; version 3; serial; inner and outer
   signature algorithms must match; issuer and subject as raw DER plus parsed RDNs for display;
   validity; SubjectPublicKeyInfo for rsaEncryption and id-ecPublicKey (prime256v1, secp384r1);
   extensions: basicConstraints, keyUsage, extKeyUsage, subjectAltName (dNSName, iPAddress),
   authority/subject key identifiers, nameConstraints (dNSName permitted/excluded subtrees
   enforced; any other constraint form makes the path invalid); an unknown critical extension is
   an error. Signature algorithms: sha256/384/512WithRSAEncryption, RSASSA-PSS with its parameters,
   ecdsa-with-SHA256/384. SHA-1 and MD5 are rejected.
3. Path building: leaf plus the server's untrusted certificates in any order (extras and
   duplicates allowed), candidates by name (and AKI/SKI when present), depth limit 8, backtracking
   over alternatives, loop detection. For each link: signature valid, validity covers the given
   Unix time, issuers are CAs (basicConstraints cA=true, pathLenConstraint honoured, keyUsage
   keyCertSign when keyUsage is present), leaf has serverAuth when extKeyUsage is present and is
   not a CA. The trust anchor is identified by subject + public key.
4. Host names (RFC 6125): subjectAltName only (no CN fallback; no SAN means reject), ASCII
   case-insensitive, a single left-most wildcard label matching exactly one label, never
   `*.com`-style two-label wildcards, IP-literal hosts match iPAddress SANs only.
5. Root store: `scripts/fetch-roots.py` downloads the Mozilla-derived bundle published by the curl
   project (https://curl.se/ca/cacert.pem, MPL-2.0 data), pins its SHA-256, and generates a Rust
   source file with every root's DER (committed). THIRD_PARTY_NOTICES.md records it.
6. API: `verify_server_chain(chain_der: &[&[u8]], host: &str, now_unix: u64, roots: &TrustStore)
   -> Result<VerifiedChain, X509Error>`; `VerifiedChain` exposes the leaf public key (for TLS
   CertificateVerify) and display names for the UI.

## Test data and tests
- `scripts/make-test-pki.sh` (the Homebrew `openssl` 3.6 CLI): a test root, an intermediate with
  pathLen 0, leaves with SANs (exact, wildcard, IP), a leaf with the wrong EKU, an expired leaf, a
  leaf signed by an intermediate that is not a CA, a name-constrained intermediate. Committed as DER
  fixtures, reused by M8-T5 for its local TLS server.
- `scripts/capture-chains.py` (Python 3.14 `SSLSocket.get_unverified_chain()`): captures the chains
  served by example.com, www.google.com, github.com, www.cloudflare.com, letsencrypt.org and
  api.anthropic.com (handshake only, no requests) with the capture time; committed as fixtures and
  validated at that time against the root store.
- x509-limbo (github.com/C2SP/x509-limbo, the test-suite JSON, pinned by SHA-256): run the
  `webpki::` and `rfc5280::` cases that apply to a TLS server-auth client; report the pass count;
  every failing case must map to a documented unsupported feature listed in the crate README.
- Negative and robustness tests: wrong host, expired at a later time, missing intermediate,
  self-signed leaf, non-CA issuer, pathLen exceeded, EKU mismatch, name-constraint violation,
  unknown critical extension; corrupting fixture DER at every byte offset never panics.
