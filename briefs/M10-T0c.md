# Brief M10-T0c — otter-part: MBR and GPT partition tables

## Goal
The laptop demo keeps models and `/config` on a FAT32 data partition of the boot stick, and the
QEMU disks will be partitioned the same way. The kernel must find partitions on any block device
(virtio-blk now, USB mass storage in M10) without trusting the bytes it reads. Crate
`crates/otter-part`, passing `crates/otter-part/tests/oracle.rs` (orchestrator, unchanged; its
header is the exact API and the rules, including which table wins on hybrid disks and when the
backup GPT is used).

## Applies
D2, D27: `#![no_std]` + `alloc`, zero dependencies, `#![forbid(unsafe_code)]`. Add `otter-part` to
`crates/Cargo.toml` members (single-line edit; other agents edit that file too). Files under ~600
lines (e.g. `lib.rs`, `crc.rs`, `guid.rs`, `mbr.rs`, `gpt.rs`). Never run git
checkout/restore/reset/stash/clean. Tests only via `scripts/verify-crate.sh` or
`scripts/memguard.py`. Do not edit the oracle.

## Design notes
- CRC-32: table-driven (a `const` 256-entry table built by a `const fn`), reflected polynomial
  0xEDB88320, initial and final XOR 0xFFFFFFFF.
- Never index a buffer with a value read from disk without a bounds check; compute LBAs and sizes
  with checked arithmetic (a header can claim any number). Validate a GPT header completely
  (every rule in the oracle header) before reading its entry array.
- Read the entry array sector by sector into one buffer sized from the validated header.
- `Guid::parse` accepts exactly 8-4-4-4-12 hex digits (either case); `Display` prints upper case.
